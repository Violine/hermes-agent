# Приоритетный список задач: доменная функция и HTTP API

Это изолированный учебный проект для проверки команды. Нужны два самостоятельно проверяемых результата: библиотека правил списка и её HTTP-представление. Не создавать UI, БД, auth, deploy или сетевой сервер.

REQ-1. В internal/tasklist добавить модель Task с JSON-полями id, title, status, priority и функцию отбора/сортировки. Статусы todo/doing/done, приоритет P0/P1/P2/P3. Опциональный фильтр status: пустое значение = все, неизвестный статус = ошибка. Порядок: P0 перед P1/P2/P3, равный приоритет — id лексикографически. Не мутировать исходный слайс. Невалидные status/priority внутри входных задач = ошибка, даже если фильтр скрыл бы эту задачу. Пустой результат должен сериализоваться JSON-массивом [], не null. Покрыть границы unit-тестами.

REQ-2. В internal/httpapi добавить GET /tasks?status=... с фиксированным демонстрационным набором: {id:t1,title:Tests,status:todo,priority:P1}, {id:t2,title:Build,status:doing,priority:P0}, {id:t3,title:Docs,status:done,priority:P2}. Использовать доменную функцию. Успех: 200, application/json, тело — массив задач; неизвестный фильтр: 400, JSON объект с непустым полем error. Повторяющийся query status и неожиданные query параметры можно обрабатывать стандартным URL.Query().Get без специальных правил. Пустой status = все. Запросы на endpoint другими HTTP методами = 405. GET /health сохраняет текущее поведение. Добавить HTTP тесты с httptest: без фильтра, три статуса, ошибка фильтра, метод, регрессия health.

Обязательные проверки: go test ./..., go test -race ./..., go vet ./... . Не добавлять внешние зависимости. Scope ограничен internal/tasklist и internal/httpapi. Планировщик сам выбирает имена функций и согласует контракты в DESIGN. Готовность: два результата проверены независимыми reviewer и QA и собраны в локальную интеграционную ветку; main остаётся исходной.
