# Параллельная разработка и пакетная регрессия

Для новых конфигураций поведение остаётся последовательным: `max_parallel_tasks=1`, без `execution_policy` каждая задача проходит все доверенные команды. Включение нового режима задаётся явно.

Верхний уровень конфигурации:

```json
{"max_parallel_tasks": 2}
```

Это максимум одновременно назначенных независимых реализаций, а не обещание двух свободных слотов провайдера. Реальное выполнение дополнительно ограничено `quota.pools.*.max_concurrent` и настройками Kanban Hermes. Глубина рассуждений и модель ролей не меняются.

В настройках проекта указывается полный список доверенных `checks` и политика выбора быстрых команд:

```json
{
  "checks": [
    ["./gradlew", "--no-daemon", ":backend:test"],
    ["npm", "--prefix", "frontend", "ci"],
    ["npm", "--prefix", "frontend", "run", "lint"],
    ["npm", "--prefix", "frontend", "run", "test"],
    ["npm", "--prefix", "frontend", "run", "build"]
  ],
  "execution_policy": {
    "version": 1,
    "full_after_tasks": 2,
    "path_rules": [
      {"name": "backend", "prefixes": ["backend/", "db/"], "quick_check_indexes": [0]},
      {"name": "frontend", "prefixes": ["frontend/"], "quick_check_indexes": [1, 2, 4]}
    ]
  }
}
```

Индексы начинаются с нуля и адресуют точные команды списка `checks`. Правило frontend включает установку зависимостей, lint и сборку; полный frontend test выполняется в пакетной регрессии. Для backend остаются обязательными unit-тесты и независимая проверка рискованных сценариев задачи. Testcontainers запускается через существующий изолированный backend runner. Политика не отменяет проверки AC или дополнительные требования безопасности проекта.

Если хотя бы один фактически изменённый путь не покрыт правилами, выбирается весь список. Общая сборочная конфигурация и неизвестные области поэтому не получают необоснованного сокращения проверок. План выбора хранит точные argv, пути и SHA-256 снимка политики.

Порядок работы:

1. Контроллер назначает до двух готовых независимых задач; рабочие копии и владение файлами разделены.
2. Автор пишет код и выполняет выбранные быстрые проверки. Независимые review и QA проверяют текущий SHA и требования задачи.
3. Контроллер собирает локальную промежуточную ветку. `staging_sha` может опережать `accepted_regression_sha`; такие задачи ещё ждут регрессии.
4. После накопления `full_after_tasks`, завершения доступной группы зависимостей или перед итоговой приёмкой запускается весь набор на неизменяемом SHA. Ошибки нескольких команд собираются в общий отчёт.
5. Ошибки возвращаются команде одним пакетом исправлений с новым review/QA. Успешная регрессия обновляет `accepted_regression_sha`. Владелец принимает только полностью проверенный результат.

Общая process-safe блокировка тяжёлых тестов: `${TEAM_DATA}/.heavy-test.lock`. Прямые команды берут её в Git gate; делегированный backend job берёт её в хостовом worker. Внешний gate не удерживает её при ожидании этого worker, чтобы исключить вложенную взаимную блокировку.

В панели «Команда → Задачи» видны промежуточный статус проверки и раскрываемый раздел «Время работы и объём кода». Подробный расчёт запускается кнопкой; обычное обновление доски не выполняет дорогой Git-подсчёт. Отчёт отличает время запусков от расхода подписки и считает строки по диапазону Git, включая отдельные категории тестов и документации. Неизвестные показатели остаются неизвестными.

Настройки проекта фиксируются при старте запроса. Уже выполняющийся запрос требует отдельной явной миграции с сохранением прежней политики и журнала; изменение конфигурации не переопределяет старое evidence автоматически. Возврат к последовательному режиму выполняется изменением `max_parallel_tasks` на 1, без удаления результатов и промежуточных коммитов.

Для одной проверенной конфигурации использовались два независимых worker-слота и пакет после двух задач. Изменения `compose.yaml` и `compose.release.yaml` покрыты отдельным правилом `compose-syntax`: шестая доверенная команда разбирает оба YAML-файла и проверяет наличие непустого `services`. Это проверка синтаксиса и структуры; она не подменяет проверку подстановки переменных через `docker compose config`. Требования задачи к feature toggle дополнительно проверяют review и QA.

При смене политики исходные отчёты сохраняются. Если старый отчёт имел `verdict=blocked` из-за проверки, перенесённой в пакетную регрессию, новый reviewer/QA самостоятельно выдаёт новый вердикт по действующему плану на том же SHA. Контроллер не переписывает прежний вердикт. Повторная карточка зависит от готовой реализации, а прежняя попытка служит историей: её блокировка не должна останавливать повтор.

Интегратор также различает предварительную готовность и завершённую регрессию. Gate со `status=deferred` допустим только при `mode=quick`, с совпадающим `policy_sha256` и точным непустым списком `deferred_checks` из действующего плана (объекты `index`, `name`, `argv`, `sha256`). Произвольный пропуск, перенос обязательной быстрой команды или ссылка только свободным текстом не разрешают интеграцию. Старый отчёт без машинной привязки сохраняется как история; интегратор формирует новый отчёт, не объявляя отложенные проверки успешными.
