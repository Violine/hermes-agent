# Руководство пользователя

Для новых задач используйте [подачу через Telegram и дашборд с согласованиями владельца](OWNER-WORKFLOW.md). Для новых запросов требования и итоговый результат всегда требуют решения владельца; отдельное согласование плана требуется по умолчанию, но его можно отключить настройкой `auto_start_after_judge_accept` после решения `accept` судьи.

## Что делает команда

Ты передаёшь краткое или полное ТЗ координатору. Система сохраняет исходный brief, запускает анализ требований, технический дизайн и планирование. Перед разработкой скептик и проектировщик проверок независимо разбирают план параллельно; судья проверяет их evidence и выносит решение. При необходимости планировщик получает ограниченный цикл исправлений. После принятия плана идут кодовые задачи, а для каждой реализации независимые reviewer и QA проверяют один commit в отдельных worktrees. Интегратор проверяет комплект evidence, контроллер применяет проектные проверки к локальной integration branch и сообщает готовую ветку для решения владельца.

Это описание установленного workflow, а не заявление, что вся цепочка уже прошла end-to-end проверку. Перед выводом о готовности установленной версии сверь актуальные evidence в [VALIDATION.md](VALIDATION.md); установленные профили и успешная отдельная роль сами по себе не доказывают прохождение всего pipeline.

Поток:

```text
ТЗ → analyst → SPEC → planner/architect → DESIGN + PLAN (snapshot/hash)
   → skeptic ∥ test-designer → judge → [planner corrections ≤ 2]
   → разработчики по зависимостям → reviewer ∥ QA → integrator
   → доверенные регрессионные команды → локальная integration branch → решение владельца
```

Первая версия принимает **одну активную фичу за раз** и исполняет кодовые задачи последовательно в топологическом порядке. Задачи reviewer и QA выполняются параллельно на одном immutable SHA. Hermes dispatcher имеет глобальный лимит три активные задачи (включая machine-owned root card) и лимит одна активная задача на профиль, поэтому review и QA занимают оставшиеся два слота. На доске будет feature/root card и отдельные карточки ролей и задач; подзадачи отражают исполнителя, приоритет и зависимости.

## Веб-интерфейс команды

В меню темы доступен вариант **Hermes · единый стиль**: общий системный шрифт для меню, страниц и диалогов, согласованные размеры полей и кнопок, прежняя зелёная палитра и видимая горизонтальная прокрутка канбана. Для кода и журналов сохранён моноширинный шрифт. Вкладка «Команда» наследует выбранную тему Hermes. Панель сохранения закреплена в пределах содержимого вкладки. При обновлении стилей перезагрузите страницу; смена темы выполняется через меню оформления в боковой панели.

Внизу бокового меню откройте выбор языка и укажите **Русский**. Выбор сохраняется в этом браузере; на другом устройстве язык нужно выбрать отдельно. Переведены оболочка, основные страницы настроек, диалоги и нативные плагины канбана и достижений. Названия моделей, идентификаторы, пути, код, пользовательские задачи, исходные журналы и внешняя документация не переводятся. Некоторые описания каталогов и диагностические сообщения поступают с сервера на исходном языке. Обслуживание перевода описано в [DASHBOARD-LOCALIZATION.md](DASHBOARD-LOCALIZATION.md).

Откройте настроенный URL командной панели. Нативная доска Hermes доступна через маршрут `/kanban`; обе ссылки задаются установкой и могут отличаться между окружениями. На вкладке **Обзор** нажми **Открыть канбан**, чтобы выбрать именно `engineering-team` и перейти к карточкам. Она содержит четыре вкладки:

- **Обзор** — состояние контроллера, активные фичи и карточки ролей. Статусы и ожидания квоты обновляются автоматически примерно каждые 10 секунд. Перед переходом **Открыть канбан** выбирает доску `engineering-team` в интерфейсе Kanban. Канбан хранит выбор доски в localStorage браузера, поэтому прямой переход по `/kanban` может показать доску, выбранную ранее.
- **Роли и модели** — для каждой роли можно выбрать provider, model, reasoning effort, бюджет запуска, число ходов и пул квоты. Пока список выбора моделей пуст, работают основные поля роли. Если добавить кандидатов, список полностью заменяет основные provider/model/effort: первый клик автоматически добавляет текущую основную модель кандидатом с приоритетом 0 и создаёт следующую строку для настройки. Не добавляйте кандидатов, пока не выбраны их модель и соответствующий пул.
- **Подписки** — включение квотных пулов, лимит параллельных запусков, резерв проверок, допустимый возраст снимка и правило на случай неизвестной квоты. Чекбокс «Авторизация настроена» — отметка оператора после входа в Hermes; это не результат проверки токена. Снимки и окна расхода показываются отдельно, когда источник их предоставил.
- **Проекты** — checkout, базовая ветка, timeout и команды регрессии. Команды редактируются как JSON-массив массивов аргументов, например `[["go","test","./..."],["go","vet","./..."]]`; это не shell-строки. Путь уже настроенного проекта защищён от редактирования, сам такой проект нельзя удалить. Для нового проекта укажите абсолютный путь, доступный серверу Hermes.

Актуальные подключения подписок и назначение моделей видны во вкладках «Подписки» и «Роли и модели». Наличие провайдера в списке выбора само по себе не подтверждает авторизацию. Веб-форма не принимает пароли и токены: настройте вход в Hermes отдельно, затем отметьте авторизацию пула.

Controller автоматически перечитывает сохранённую конфигурацию на каждом цикле работы; для обычного изменения настроек перезапускать его не нужно. Новые настройки ролей применяются к новым карточкам. Для уже созданных карточек сохраняются снимки назначений; смена provider/model/effort блокируется, пока у роли есть карточка со статусом `ready` или `running`. После завершения такой карточки можно сохранить новое назначение для следующих задач.

## Выбор папки для доски

В «Новая доска» и «Настройки» рядом с каталогом проекта нажмите **«Обзор…»**, откройте нужный каталог и нажмите **«Выбрать эту папку»**. Показываются папки сервера, доступные Hermes. Выберите каталог проекта под настроенным workspace root; конкретный путь зависит от установки. Ограничения и сценарии выбора каталога описаны в [руководстве по folder picker](FOLDER-PICKER.md).

| `team-judge` | Проверяет evidence findings и решает принять план, вернуть на исправление или запросить решение владельца | High |

| `team-qa` | Независимые функциональные и регрессионные проверки | Medium |
| `team-integrator` | Проверка gate-артефактов и подготовка интеграционного решения | High |
| `team-coordinator` | Ведёт board и переходы; в первой версии основную lifecycle автоматику выполняет controller | High |

Preset развёртывания: analyst, planner, skeptic, test-designer, judge, reviewer и integrator — high; разработчики — low; QA — medium. У каждого профиля отдельно задаются provider, model, reasoning effort, лимит ходов и бюджет выполнения. Effort — значение из набора, который поддерживает Hermes (`none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, `ultra`). Если транспорт провайдера его игнорирует или не поддерживает, нельзя считать effort применённым: проверьте фактическую конфигурацию/ответ адаптера.

Для быстрой/повседневной реализации preset предлагает low; для анализа, дизайна и ревью — high. Изменяйте отдельно по своей цене, скорости и качеству на реальных задачах. Не задавайте модель в `SPEC.md`, `PLAN.json` или role prompts: источник настройки — JSON конфигурация роли.

### Модели и подписки

На сервере подключён только Kimi Coding. Успех одного профиля с Kimi не доказывает, что Kimi доступен из каждого изолированного профиля: проверяйте provider/auth у worker, а не только в общем Hermes gateway.

Codex и Claude Code **не считаются подключёнными** только потому, что у владельца есть подписка или CLI на Mac. Нужно подтвердить серверную авторизацию, поддерживаемый Hermes transport/adapter и правила использования конкретного плана; провести короткий тест одним профилем без публикации токенов. Не подставляйте токен подписки как API key, если провайдер это явно не поддерживает. Не делайте вывод, что Codex/Claude subscription auth работает через этот Hermes launcher, пока это не проверено фактическим end-to-end запуском.

Данные авторизации настраиваются отдельным способом установщика. Конфиг команды хранит имена provider/model/effort, но секреты не должны попадать в README, задачи, артефакты, логи или Git. Ролевые профили — конфигурационная изоляция, а не security boundary: все агенты работают от одного Unix-пользователя и используют общую файловую систему Hermes, поэтому агент потенциально может прочитать другие доступные этому пользователю auth-файлы. Не полагайтесь на profile/worktree как на ACL и не помещайте в среду credentials, которые не готовы раскрыть исполняемому агенту. Перед использованием проверьте актуальные права и credential forwarding. Не копируйте default-профиль Hermes вместе с его памятью/каналами в рабочие профили без явного решения.

#### Лимиты и квотные пулы

Пулы квот назначаются явно и используются как верхняя граница маршрутизации, а не как разрешение автоматически покупать платные запросы. Если выбранный пул исчерпан, агент не должен незаметно переключаться на другой аккаунт, provider с оплатой за запрос или новый бюджет. Поток останавливается/ограничивается согласно настроенной политике и показывает владельцу причину. По умолчанию оставляй резерв 20% доступного лимита для проверки/закрытия задач: обычные роли получают запуск только когда остаток выше резерва, а validation-роли (`skeptic`, `test-designer`, `judge`, `reviewer`, `qa`, `integrator`) могут использовать зарезервированную часть. Резерв — порог допуска, а не точный прогноз стоимости токенов.

Пул задаётся в `quota.pools.<pool-id>` с `provider`, `enabled`, `auth_ready`, `max_concurrent`, `reserve_percent`, `max_snapshot_age` и `unknown_policy`; `auth_ready` — подтверждаемая оператором настройка, а не автоматическая проверка учётной записи. При `config init` также может быть указан `probe` (`kimi`, `codex` или `anthropic`). На текущем runtime probe helper выбирается по `provider`; не меняй `probe` в расчёте переключить helper, пока это поле не подключено к фактической маршрутизации. У роли можно указать один `pool` либо `candidates` с `pool`, `provider`, `model`, `reasoning_effort` и явным `tier`; ниже tier — предпочтительнее. Если `candidates` не пуст, он полностью заменяет основные provider/model/effort этой роли. Веб-интерфейс при первом добавлении кандидатов включает основную модель как tier 0; последующие варианты добавляйте явно. Сам список не подключает подписки и не включает оплату. При старте каждого задания менеджер создаёт lease на пул; параллельность пула и возраст usage snapshot ограничивают новые запуски.

Пример полей (добавьте их в общий `config.json`, не вставляя секреты):

```json
{
  "quota": {
    "pools": {
      "kimi-main": {
        "provider": "kimi-coding",
        "enabled": true,
        "auth_ready": true,
        "max_concurrent": 2,
        "reserve_percent": 20,
        "max_snapshot_age": 180,
        "unknown_policy": "wait",
        "probe": "kimi"
      }
    }
  },
  "roles": {
    "team-analyst": {
      "provider": "kimi-coding",
      "model": "kimi-k2.6",
      "reasoning_effort": "high",
      "pool": "kimi-main"
    }
  }
}
```

Используй `enabled: true` и `auth_ready: true` только после проверки выбранного provider/auth. Поле `probe` в default config — одно из `kimi`, `codex`, `anthropic`; сейчас его фактический выбор производится по `provider`. Не добавляй candidate как «резерв» если не хочешь разрешить реальную маршрутизацию к этому пулу. Источники Hermes читают по одному глобальному auth source на provider; несколько pool IDs одного provider не означают отдельные аккаунты и не могут безопасно балансироваться между подписками. Такие дублирующиеся pools останутся `unknown`.

Если provider не умеет надёжно опрашивать квоту, считай её неизвестной. Безопасное значение `unknown_policy` — `wait`. Ограниченный запуск под неизвестной квотой возможен только при явном решении владельца: выбрать в UI **«Один запуск при неизвестной квоте»** (`allow_limited`) для конкретного пула. Тогда разрешается не более одной одновременно активной unknown-limited lease на этот пул. Точный остаток и расход заранее неизвестны, поэтому вызов может упереться в уже исчерпанный лимит. Контроллер не включает такой режим автоматически для Kimi или любого другого provider. Это не разрешает paid fallback. Не задавай эту политику по умолчанию. При неизвестной квоте без opt-in — не запускай worker.

Проверяй quota status перед серией запусков и после обновления/возобновления. Показанные остатки основаны на usage snapshot и могут устареть или измениться вне controller; смотри время/источник snapshot и lease. `quota refresh` запускает read-only probe и обновляет snapshot; ошибка переводит состояние в `unknown`, а не сохраняет предыдущий «здоровый» остаток. Ledger, status и refresh не выводят credentials. Пока источник Kimi не различает usage отдельных клиентов одного аккаунта, изменение процентов нельзя приписать конкретной задаче.

Источники, поддерживаемые endpoints, ограничения OAuth/API и дата последней ручной read-only проверки описаны в [QUOTA-SOURCES.md](QUOTA-SOURCES.md). Значение probe — моментальный общий usage аккаунта: не трактуй изменение процентов как расход конкретной фичи или Hermes-задачи.

```bash
docker exec <hermes-container> /path/to/hermes-team/runtime/scripts/teamctl quota status
docker exec <hermes-container> /path/to/hermes-team/runtime/scripts/teamctl quota refresh
```

Изменяй пул и явные модели через `config set-pool` и `config set-candidates`, используя JSON-файлы без секретов. Путь к файлу должен быть абсолютным и доступным внутри контейнера; передай файлы в контейнер разрешённым способом:

```bash
docker exec <hermes-container> /path/to/hermes-team/runtime/scripts/teamctl config set-pool kimi-main --file /absolute/path/pool.json
docker exec <hermes-container> /path/to/hermes-team/runtime/scripts/teamctl config set-candidates go --file /absolute/path/go-candidates.json
```

`set-candidates` разрешает роли использовать только явно перечисленные пары provider/model/pool/effort; не включай кандидата как неявный платный резерв. После добавления candidates меняй модель/effort через `set-candidates`, потому что `set-role --provider/--model/--effort` для такой роли отклоняется.

Контроллер автоматически перечитывает конфигурацию на каждом цикле работы. После сохранения через веб-интерфейс или CLI обычный перезапуск `hermes-team-controller.service` не требуется. Новые настройки ролей применяются к новым карточкам. Уже созданные карточки, включая ожидающие квоты, сохраняют снимок назначений и списка кандидатов; смена конфигурации не переносит запущенную работу к другому провайдеру. Изменение provider/model/effort отклоняется, пока у роли есть карточка `ready` или `running`. Изменения пулов учитываются при следующей проверке допуска.

## Onboarding проекта

Подключайте проект только после проверки его Git checkout, правил работы и локального цикла проверки. Чтобы подготовить повторно используемые документы на любом реальном проекте, передайте агенту задание из [PROJECT-ONBOARDING-PROMPT.md](PROJECT-ONBOARDING-PROMPT.md), запущенное в корне соответствующего репозитория. Оно не требует установки Hermes в целевом проекте. Владелец проверяет diff и вопросы агента, затем самостоятельно коммитит manifest и документы в проект; controller читает только файлы, зафиксированные в выбранной base revision.

1. Укажите стабильный ключ проекта и **абсолютный путь** к checkout. Выберите base ref, из которого контроллер будет создавать задачные ветки. Контроллер требует чистое исходное рабочее дерево при запуске фичи и проверяет, что base ref не переместился во время выполнения.
2. Прочитайте корневой `AGENTS.md`/`CLAUDE.md`, README/CONTRIBUTING и релевантные правила проекта. Инвентаризируйте `.spec/` и прочитайте документы по затрагиваемым компонентам; запишите конфликты и фактически прочитанные источники в дизайне. Не выводите правила по аналогии с чужим стеком.
3. Определите owner boundaries для указанных путей из официального файла владения проекта (например, CODEOWNERS) и связанных README. Если владелец неизвестен или правила расходятся — оставьте видимый вопрос, не выдумывайте команду-владельца.
4. Выберите **доверенные регрессионные команды** и настройте их как массивы argv: каждая команда — список аргументов, например `[["./gradlew", ":service:test"], ["go", "test", "./..."]]`. Это не shell-строки: не используйте `&&`, `|`, `$()` или перенаправления; добавляйте отдельную запись на каждую команду. Контроллер запускает их непосредственно в локальной integration worktree, с timeout проекта и проверкой, что команды не меняют кандидат. Команды выполняются с правами общего пользователя Hermes; добавляйте только доверенные проверки, которые безопасны в этой среде. Не добавляйте команды, которые удаляют данные, работают против production, публикуют артефакты, требуют интерактивного секрета или обращаются к внешним системам без необходимости и безопасной изоляции.
5. Команды должны быть достаточны, чтобы зафиксировать необходимую регрессию: targeted сборка/линт/тесты затронутых компонентов плюс нужные интеграционные проверки по проектной политике. Команды reviewer/QA — отдельный их выбор по роли, но обязательные project argv являются блокирующими gates и выполняются при интеграции. Выберите реалистичный timeout.
6. Для frontend/mobile укажите наличие браузера, SDK, toolchain, устройств/эмуляторов и тестовых credentials/данных через безопасный секретный канал. Неприменимость сценария объясните в coverage limitations/findings. Не используйте `skip` в QA `checks`: обязательные выбранные команды должны иметь фактические результаты, а отложенные быстрые планом проверки отражаются только отдельным точным `deferred` binding. Если отсутствует обязательная среда для выбранной проверки, QA сообщает `blocked`, не имитируя успешное тестирование.
7. Для каждого task в плане нужны относительные `owned_paths`. Контроллер не пропускает изменения вне заявленных границ; `.git`, `.env`, абсолютные и слишком широкие пути запрещены контрактом.

### Контекст проекта для карточек

Опциональный manifest `.agents/project.json` связывает проект с его паспортом и документами компонентов. Формат версии 1 описан в [PROJECT-ONBOARDING-PROMPT.md](PROJECT-ONBOARDING-PROMPT.md); сам manifest и перечисленные документы должны быть committed в проекте до того, как их сможет прочитать Hermes. Он хранит стабильное имя/описание, стек, относительные ссылки на документы, component path scopes и просмотренные внешние источники. Он не является источником истины для фактов о текущем коде.

Для зарегистрированного проекта доступны настройки `context_file` (по умолчанию `.agents/project.json`) и `context_required` (по умолчанию `false`). Контекст необязателен: проект без manifest продолжает работать по прежнему workflow, если владелец не включил обязательный режим. На вкладке **Проекты** можно изменить эти настройки и нажать **Проверить контекст**. Предпросмотр проверяет manifest и перечисленные файлы только в tracked Git-ревизии проекта; он не запускает команды, не проверяет истинность архитектурных утверждений и не заменяет review человеком.

CLI предпросмотра:

```bash
teamctl config project-context <project-key>
teamctl config project-context <project-key> --write /absolute/path/context-packs
```

Первый вариант показывает проверяемый preview. `--write` принимает каталог и сохраняет неизменяемый пакет в подкаталог с hash (`<каталог>/<context-hash>/PROJECT-CONTEXT.md` и `context.json`); используйте каталог артефактов вне репозитория. В задачи передаются путь и ревизия пакета, применимые документы выбираются по затронутым путям, затем агент проверяет критичные факты на candidate SHA и учитывает вложенные `AGENTS.md`/`CLAUDE.md`. Пакет закреплён на момент запуска роли; последующее изменение конфигурации не переписывает уже созданную/запущенную карточку. Новая ревизия применяется к новым задачам после commit.

Проверьте preview перед включением `context_required`: обязательный отсутствующий или некорректный manifest должен остановить допуск новой работы с понятной причиной. Обнаруженное противоречие в проектных документах агент обязан вынести владельцу; неизвестное нельзя превращать в соглашение. Команды из `DEVELOPMENT.md`/`TESTING.md` считаются описанием проекта, а не автоматически доверенной конфигурацией запуска controller.

### Важное для мобильной разработки

Инструкция `team-mobile` уже существует, но мобильные SDK и end-to-end toolchain пока не готовы. Сейчас этот профиль может исследовать репозиторий, подготовить дизайн или выполнить проверяемую задачу только если конкретный SDK, build variant, лицензии/доступы, устройства/эмуляторы и тестовые команды доступны в проектной среде. До onboarding Android/iOS среды не выдавайте мобильные build, UI, lifecycle или device checks за пройденные. Для невозможной обязательной проверки — блокируйте карточку с названием недостающего SDK/устройства/доступа и командой, которую надо добавить.

## JSON конфигурация

Контроллер читает файл по умолчанию из `/path/to/hermes-team/config.json` (можно переопределить `--config` или `HERMES_TEAM_CONFIG`). Текущая реализация использует следующую структуру; итоговую конфигурацию и установочную команду сверяйте с установленной версией controller CLI.

```json
{
  "hermes_root": "/path/to/hermes-home",
  "data_root": "/path/to/hermes-team/data",
  "bundle_root": "/path/to/hermes-team/runtime",
  "board": "engineering-team",
  "poll_seconds": 5,
  "max_active_features": 1,
  "auto_start_after_judge_accept": false,
  "max_plan_tasks": 12,
  "max_plan_report_retries": 1,
  "max_report_retries": 1,
  "max_plan_corrections": 2,
  "max_rework_rounds": 2,
  "roles": {
    "team-analyst": {
      "provider": "<проверенный Hermes provider>",
      "model": "<доступная model id>",
      "reasoning_effort": "high",
      "max_turns": 40,
      "run_budget": 600,
      "toolsets": ["file", "terminal", "kanban"]
    }
  },
  "projects": {
    "<project-key>": {
      "repo": "/absolute/path/to/clean/repository",
      "base_ref": "main",
      "checks": [["<tool>", "<arg>"], ["<tool>", "<another-arg>"]],
      "check_timeout": 180,
      "context_file": ".agents/project.json",
      "context_required": false
    }
  }
}
```

Значения путей и `board` в примере — демонстрационные; они должны совпадать с развертыванием. `data_root` должен быть вне checkout. Полный `roles` map должен содержать нужные team-профили и настройки provider/model/effort для каждого. Не помещайте API keys/passwords в JSON. Установка профиля, права файлов и VPN namespace сами по себе не дают межагентный контроль доступа; считайте, что роль может прочитать файлы общего Unix-пользователя.

Поддерживаемые поля профиля в установщике: `provider`, `model`, `reasoning_effort`, `max_turns`, `run_budget` (секунды), `toolsets`, `description`, `role_doc` или `role_docs`, опционально явный allowlist имён env credential vars. Не добавляйте переменную в allowlist до проверки, что она необходима конкретному provider; значение не должно логироваться. Allowlist сокращает случайную передачу env, но сам по себе не ограничивает чтение credential-файлов с общей файловой системы.

На уровне controller карта `roles` включает профили `team-analyst`, `team-planner`, `team-skeptic`, `team-test-designer`, `team-judge`, `team-backend`, `team-frontend`, `team-mobile`, `team-go`, `team-reviewer`, `team-qa`, `team-integrator`, `team-coordinator`. Каждый активируемый профиль должен содержать собственные `provider`, `model` и `reasoning_effort`; можно назначать разные значения разным ролям. Установщик может построить стартовый набор с общим provider/model и разным effort, после чего конфигурация редактируется по отдельности. В контроллере `projects.<key>` ожидает `repo`, `base_ref`, непустой `checks` как список argv-массивов и необязательный `check_timeout`; контекст настраивается опциональными `context_file` (строка, default `.agents/project.json`) и `context_required` (boolean, default `false`).

## Команды и подключение проекта

Командой управляет `teamctl`, установленный внутри VPN-контейнера Hermes по пути `/path/to/hermes-team/runtime/scripts/teamctl`. Конфигурация хранится в `/path/to/hermes-team/config.json`, а native Hermes board называется `engineering-team`. Команды ниже запускаются на домашнем сервере и используют Docker; не запускайте одноимённый Mac-процесс, если конфигурация не синхронизирована.

Проверить статус и роли:

```bash
docker exec <hermes-container> /path/to/hermes-team/runtime/scripts/teamctl status
docker exec <hermes-container> /path/to/hermes-team/runtime/scripts/teamctl config show
```

При первой настройке, если конфиг ещё не существует, команда `config init` создаёт default role profiles с `kimi-coding` / `kimi-k2.6` и presets усилия. После этого изменяйте профили и подключайте проект отдельными командами `set-role` / `add-project`; `init` не перезапускайте поверх существующей конфигурации.

```bash
docker exec <hermes-container> /path/to/hermes-team/runtime/scripts/teamctl config init
```

Добавить проект с чистым checkout и доверенными регрессионными командами:

```bash
docker exec <hermes-container> /path/to/hermes-team/runtime/scripts/teamctl config add-project demo \
  --repo /absolute/path/to/repository \
  --base main \
  --checks-json '[["go","test","./..."],["go","vet","./..."]]' \
  --timeout 180 \
  --context-file .agents/project.json \
  --context-required
```

Имя проекта — стабильный ключ, который передаётся в `submit`; checkout и base должны существовать и быть доступны **по этому пути внутри контейнера**. Перед добавлением проверок запустите их вручную в чистой тестовой копии. Для argv используйте массивы аргументов — это не shell-строки: не указывайте `&&`, `|`, `$()` или перенаправления. Controller запускает команды прямо в локальной integration worktree, с настроенным timeout, и проверяет, что проверка не изменила candidate. Не добавляйте команды, которые удаляют данные, работают с production, публикуют артефакты или обращаются к внешней системе без безопасной изоляции.

`--context-file` и `--context-required` необязательны; при отсутствии параметров используется `.agents/project.json` и необязательный режим. Проверить доступность контекста на committed base revision можно так:

```bash
docker exec <hermes-container> /path/to/hermes-team/runtime/scripts/teamctl config project-context demo
docker exec <hermes-container> /path/to/hermes-team/runtime/scripts/teamctl config project-context demo \
  --write /path/to/hermes-team/data/project-context/demo
```

Preview проверяет структуру manifest и доступность перечисленных tracked документов; он не подтверждает правильность их содержания. `--write` создаёт immutable snapshot в `<переданный-каталог>/<context-hash>/`. Перед `context_required=true` разрешите все ошибки и убедитесь, что нужные документы действительно закоммичены.

Настроить provider, модель, effort и бюджет для отдельного профиля:

```bash
docker exec <hermes-container> /path/to/hermes-team/runtime/scripts/teamctl config set-role go \
  --provider <проверенный-provider> \
  --model <доступная-model-id> \
  --effort low \
  --budget 600
```

Для роли Go можно указать `go` или `team-go`. Для provider с env credentials допускается передать имя переменной через `--credential-env KEY`; секретное значение настройте отдельно и не показывайте в выводе. `config show` не должен раскрывать значения секретов.

Создать фичу. Brief должен находиться в абсолютном пути, доступном внутри контейнера:

```bash
docker exec <hermes-container> /path/to/hermes-team/runtime/scripts/teamctl submit \
  --project demo \
  --brief /absolute/path/inside/container/brief.md \
  --title "Краткое название фичи" \
  --id demo-priority
```

Если brief находится на Mac, скопируйте его разрешённым способом в доступный серверный каталог контейнера. Не помещайте секреты в brief и аргументы. Для изменения provider/model/effort выполните отдельный `config set-role`, затем проверьте `config show`, не раскрывая секреты. Возобновить остановленную feature после снятия blocker можно командой `teamctl resume <feature-id> --reason "<что исправлено>"`. Если причина блокировки исправлена для текущих worker-задач, добавьте `--retry-workers`, чтобы повторно разблокировать их карточки. Без флага resume продвигает только root feature card и не считает причины блокировки исполнителей устранёнными.

После установки и включения controller service lifecycle продвигается автоматически; проверить root card можно командой `teamctl status` и в Hermes board. Ручной daemon запуск нужен только для диагностики/установки, чтобы не поднять второй controller процесс.

### Границы безопасности

Hermes и worker-процессы находятся в VPN-сетевом namespace, отделённом от обычных host-приложений. Это ограничивает их сетевой маршрут и защищает другие приложения от смены host routing, но **не** разделяет роли по файловым правам. Все агенты запущены с общим Unix-пользователем; role profiles, Kanban assignment и Git worktrees не являются hard RBAC. У них общий доступ к файлам, которые видит этот пользователь, включая потенциально общие auth-файлы. Секретный env forwarding и его границы нужно отдельно проверять в установленной версии; не считайте изоляцию секретов доказанной только по наличию отдельных профилей.

## Работа и наблюдение

Создайте brief с контекстом, пользовательской проблемой, ожидаемым результатом, известными ограничениями и ссылками на документы. Если в требованиях нет ответа — аналитик/планировщик укажет точный блокирующий вопрос. Контроллер не должен превращать вопрос в выдуманное решение.

Следите за board и журналом состояния фичи. Root card отражает состояние всего потока; каждый запуск роли — отдельная native card с собственными исполнителем, run ID и статусом. Стадии: analysis → planning → plan review (skeptic и test-designer параллельно, затем judge; при revise до двух возвратов planner) → implementation → verification (review и QA) → integration review → done. По умолчанию после принятия плана судья ждёт отдельного согласования владельца; `auto_start_after_judge_accept: true` убирает только это решение и запускает реализацию автоматически после уже согласованных требований и `accept` судьи. Согласование требований и финальная приёмка остаются обязательными при любом значении. Блокировки показывают причину; сначала устраните блокер и возобновите поток, не создавайте дубликат фичи.

Артефакты фичи и промежуточные отчёты хранятся под `data_root/runs/<feature-id>/`, а не в Git checkout. Каждая версия анализа находится в отдельном `analysis-round-N/`: в ней лежат snapshot SPEC/DESIGN/PLAN, controller-generated `plan_sha256`, два независимых `PLAN-REVIEW.json` и `PLAN-DECISION.json`. Hash связывает выводы проверяющих с точным набором SPEC+DESIGN+PLAN; любое изменение этих файлов требует нового snapshot и повторного review. На `accept` разработка начинается по принятому PLAN; на `revise` планировщик получает findings судьи, не более двух раз согласно `max_plan_corrections`; на `needs_input` ждём владельца. Этот лимит отдельный от `max_rework_rounds`, который ограничивает доработку кода после review/QA. Есть также per-task TASK/IMPLEMENTATION/REVIEW/QA/INTEGRATION, журнал состояния и итоговый DELIVERY. В отчётах фиксируются точные SHA/hash, run ID, роль/исполнитель, команды, фактический исход и ограничения проверки.

Лимиты `max_plan_report_retries` и `max_report_retries` относятся только к формату/привязке отчёта. Если роль выдала отчёт неправильной схемы, не тот feature/hash/task или неверную identity, controller сохраняет исходный результат и создаёт свежую карточку той же роли через обычный quota admission; по умолчанию допускается одна такая попытка для план-review и одна для остальных отчётов. Исправление формы отчёта не меняет решение по его содержанию: содержательный `revise`, `needs_input`, blocker или непрошедший gate сохраняет свой смысл и не обходится автоматическим retry. Эти лимиты отдельны от `max_plan_corrections` и `max_rework_rounds`.

Скептик проверяет полноту scope, требования, допущения, реализуемость и риски. Test-designer отдельно проверяет связку AC → сценарий → доказательство, включая обязательные негативные и граничные проверки. Они работают независимо и параллельно, не читают findings друг друга до своего отчёта и не изменяют план. Судья рассматривает каждое замечание как `resolved`, `dismissed`, `revise` или `needs_input`; он обязан привести evidence для закрытия или отклонения. Это не голосование: `accept` допустим только после проверки обоих отчетов и разрешения каждого блокирующего finding доказательством. Судья не добавляет новые продуктовые требования. Если нужно решение по неясному scope или отсутствующий ресурс, поток блокируется для владельца.

## Независимое ревью, QA и интеграция

- Разработчик работает в выделенной ветке, меняет только owned paths, делает локальный атомарный commit и оставляет чистую рабочую копию. Push и protected branch не меняются.
- Reviewer и QA работают раздельно, на одном base/head SHA, с разными assignee и native run ID. Каждый читает свой candidate worktree; не редактирует кандидат и сохраняет отчёт вне checkout. QA не обязан ждать review. Worktree сохраняет границу файлов/Git, но не изолирует агента от файлов общего Unix-пользователя.
- `pass` возможен только с конкретным evidence и обязательными checks. Любая смена HEAD делает старые отчёты недействительными. `changes_requested` завершает карточку проверки и приводит к новой реализации/новым review и QA. Реальный вопрос доступа или неразрешимое требование — `blocked`.
- Интегратор только сверяет gates и готовит `INTEGRATION.json`; он не выполняет Git merge и не запускает итоговые проектные команды. Контроллер проверяет отчёт, затем сам объединяет локальный candidate в отдельной integration worktree/ветке, запускает доверенные project commands и создаёт локальную ветку-кандидат `codex/team-integration/<task-id>`. Ошибка регрессии не продвигает задачу.
- После успешной фичи итоговый `DELIVERY.json` содержит candidate ref и SHA. Это готовый для владельца локальный результат, не merge в protected branch. Владелец решает о просмотре и дальнейшем переносе. Push, MR, релиз, prod deploy и любые внешние публикации требуют отдельного действия/политики.

## Текущие ограничения

- Это локальная команда и локальные Git worktrees; remote SCM, создание MR, облачная сборка и деплой не выполняются автоматически.
- Кодовые задачи сейчас запускаются последовательно, даже когда часть задач независима; граф зависимостей сохраняет корректный порядок и приоритет.
- Параллелизм ограничен global limit Hermes: одна root-card активной фичи и максимум два рабочих профиля одновременно. Повторные submit во время активной фичи не создадут второй параллельный поток.
